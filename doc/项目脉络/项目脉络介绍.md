# 项目脉络介绍（文献雷达 · 科研文献持续跟踪助手）

> 这份文档不绕弯子，就干三件事：**讲清项目长什么样、每个功能靠哪些文件干活、为什么这么设计**。最后附一份「各模块知识点 + 设计理由」，当学习地图用。

---

## 0. 一句话说清这是个什么项目

**文献雷达 = 一个帮你"盯梢"科研方向的工具。**

你告诉它："我关注『大模型检索增强』这个方向。" 它就：
1. 定时去各个论文网站（arXiv、Semantic Scholar 等）把新论文抓回来；
2. 自动去重（同一篇论文别存两遍）、筛掉不相关的；
3. 存进数据库；
4. 你打开网页，看到"有 N 篇新论文"的提醒；
5. 你还能直接对它提问，甚至让它给你写一段"这个方向现在研究到哪了"的文献综述，并导出成 Word。

技术栈分三块：**后端 Python + FastAPI + MySQL**（问答会话正文另存一份本地 SQLite 检查点），**前端 Vue 3 + TypeScript**，中间夹一层**大模型（LLM）+ 检索**（含本地向量模型与 MCP 工具通道）。

## 1. 项目结构：目录是干什么的

先把目录看一遍，知道"什么代码该放哪"：

```
deep_search_pro-master/
├── main.py                 后端总入口：启动服务、建库建表、开定时器和后台队列表
├── app/                    后端「接口 + 数据」层（对外提供服务）
│   ├── routers/            各种 HTTP 接口（登录、订阅、问答、管理端……）
│   ├── schemas/            接口的「请求/返回长什么样」的定义（Pydantic 模型）
│   ├── session.py          数据库引擎/连接池 + 会话(Session)工厂
│   ├── models.py           8 张表的 ORM 模型（表结构唯一权威）
│   ├── database.py         建库建表 + 初始化引导（管理员 / 默认模型）
│   ├── security.py         密码哈希 + JWT 令牌签发/校验
│   ├── deps.py             登录校验、管理员(admin)校验（接口执行前的"门卫"）
│   └── config.py           所有配置项（从环境变量读：数据库地址、密钥、LLM key……）
├── ai/                     所有跟大模型、检索、多 Agent 有关的代码（后端最"聪明"的一层）
│   ├── orchestrator.py     QA / 综述编排大脑（LangGraph 状态图 + 会话落盘）
│   ├── llm_provider.py     所有大模型调用的统一出口（按 agent 绑定模型）
│   ├── rewrite.py          查询改写（含 quick 通道的 LLM 英文关键词兜底）
│   ├── router_agent.py     难度判定（quick / normal / deep）
│   ├── retriever.py        三通道检索（文献库 / 网络 / 历史会话）
│   ├── vector_recall.py    文献库向量召回（本地 bge 模型 + 向量缓存）
│   ├── rerank.py           精排抽象层（当前实现：BM25）
│   ├── planner.py          Planner 主 Agent（规划调度）
│   ├── reviewer.py         Reviewer 质检 Agent
│   ├── tools.py            工具层（MCP 优先 + 进程内回落）
│   ├── mcp_server.py       MCP 服务端（stdio 子进程，暴露 3 个检索类工具）
│   ├── mcp_client.py       MCP 客户端（单例连接 + 失败即标记不可用）
│   ├── analysts.py         多视角分析师集群
│   ├── summarizer.py       汇总 / 综述生成
│   ├── meta_enhance.py     元数据静态映射注入（期刊等级 / 分区等）
│   └── trace.py            运行期追踪（LLM / 工具 / 步骤事件，评测与排查用）
├── worker/                 后台干活的：定时器(scheduler) + 任务队列(queue) + 抓取管道(pipeline)
├── sources/                对接外部论文网站（arXiv / 万方 / Semantic Scholar）
├── eval/                   离线评测：cases.json 题集 + run_eval.py + record/ 测试记录
├── tests/                  pytest 用例（当前 114 例，覆盖编排四路径 / 检索 / MCP / ORM 等）
├── scripts/                一次性运维脚本（align_schema.py：模型与库结构对齐校验）
├── BAAI/                   本地向量模型 bge-large-en-v1.5
├── data/                   运行期产物：向量缓存、会话检查点 qa_checkpoints.sqlite3
├── web/                    前端（Vue 3）
│   └── src/
│       ├── views/          一个页面一个文件（工作台、问答、日志、设置、管理端……）
│       ├── components/     复用的小组件（按钮、大纲编辑器）
│       ├── api/client.ts   前端统一调用后端的"电话总台"
│       ├── router/         前端路由（哪个网址显示哪个页面）+ 登录守卫
│       ├── stores/         全局状态（比如"当前登录用户"）
│       └── layouts/        整体页面骨架（侧边栏 + 内容区）
└── doc/                    各种设计文档（PRD、详细设计、变更记录、项目脉络）

> 注：根目录下的 `api/`、`prompt/`、`tools/`、`utils/` 是**历史遗留空目录**，当前代码不使用，看代码时请忽略。
```

### 为什么这么分？

- **前端 / 后端 / 抓取 / AI 分开**：每块职责单一。改页面不用动数据库，换论文网站不用动 AI。
- **`routers`（接口）和 `schemas`（格式）分开**：接口只管"收请求、调逻辑、返结果"；格式定义单独放，前后端对字段有争议时，看 `schemas` 就是标准答案。
- **`ai/` 单独一层**：大模型相关代码最容易改来改去（换模型、改提示词），单独隔离，坏了大不了退回老流程，不连累别的功能。
- **`worker/` 单独一层**：抓论文很慢（要等外部网站），绝不能卡住用户的网页请求，所以挪到后台慢慢跑。

## 2. 先搞懂两条主流程，项目就懂了一大半

### 流程 A：后台定时抓论文（没人在网页上操作时，它自己转）

```
定时器 worker/scheduler.py
   每个一段时间检查：哪些方向"该跑了"（到点了/上次跑过了）
        ↓ 下发一个任务
任务队列 worker/queue.py
   排队、按 task_id 防重复、把任务交给对应处理函数
        ↓
抓取管道 worker/pipeline.py
   ① 增量抓取：只拉"上次之后"的新论文（用 last_run_at 当游标）
   ② 去重：靠论文唯一号(external_id) + 标题归一化比对
   ③ 打分筛选：元数据过滤 → 关键词/全文命中(BM25) → 可选大模型精筛
   ④ 入库 + 写"未读" + 写日志
        ↓
外部数据源 sources/arxiv.py、semantic_scholar.py、wanfang.py
   真正去论文网站把数据拉回来（带限速、失败重试）
```

### 流程 B：AI 问答 / 综述（你在网页上提问时才走）

```
前端 QaView.vue  →  POST /api/qa/ask
        ↓ 立即返回一个会话号，前端开始每 1.5 秒轮询"做到哪一步了"
后端接口 app/routers/qa.py
        ↓
编排大脑 ai/orchestrator.py（LangGraph 状态图，跑在后台线程里）
   图结构：8 个节点 + 条件边决定分岔与返工
   ① rewrite 查询改写 ai/rewrite.py（把你的大白话问题变成检索式）
   ② 判断难度 ai/router_agent.py，分成两条岔路：
        · quick  →（额外）先做一次 LLM 英文关键词兜底 → 直接检索 + 汇总（不请大模型规划）
        · normal/deep → plan：Planner 主 Agent 规划（ai/planner.py）
   ③ execute_tools 调工具 ai/tools.py（查库、查网、查历史、跑分析师）
        · 三个检索通道：文献库（双路召回）/ 网络 / 历史会话，按需调度、串行合并
        · 工具优先走 MCP 通道（ai/mcp_client.py → ai/mcp_server.py 子进程），失败回落进程内
   ④ summarize 先出草稿 ai/summarizer.py（带 [n] 引用编号 + 来源清单）
   ⑤ review Reviewer 质检"待交付的草稿"（ai/reviewer.py）；不过关就返工，最多 3 轮
   ⑥ finalize 收尾交付；任一步不可用 → fallback 降级收尾，链路不断
        · 会话正文每步自动落盘到本地 SQLite 检查点（LangGraph SqliteSaver）
        · (综述场景) 额外产出一份可编辑大纲，并可导出 Word
        ↓
前端轮询到"完成了"，再把结果画出来
```

**记住这两条链，剩下的都是细节。**

## 4. 为什么这么设计（几条全局大原则）

**1）为什么爬虫用普通代码，只有问答才用大模型？**
抓取、去重、入库这些活是"死的"——规则明确、结果确定，用普通代码又快又便宜又稳。大模型贵、慢、还可能胡说，只用在"需要综合判断"的地方（问答、综述）。

**2）为什么登录不立刻抓论文，而是丢到后台？**
登录时要等外部网站响应，可能好几秒。让用户干等体验极差。所以登录只做"快活"（校验密码、返回已存的数据），"慢活"（拉 API、去重、入库）交给后台 worker 慢慢做，用户界面不卡。

**3）为什么要有"定时器 + coalesce 合并错过的窗口"？**
这工具不是 7×24 常驻的（你电脑关机它就停了）。所以：
- 用"游标"记上次抓到哪，只拉增量，不重复拉全部；
- 错过的时间窗不逐个补跑，直接**合并成一次**跑（coalesce），省事又省资源。

**4）为什么去重要"唯一号 + 标题归一化"双保险？**
同一篇论文在不同网站 ID 可能不一样，光靠 ID 去不干净。所以先用论文唯一号(external_id)建**唯一索引**硬拦，再用"标题去掉标点大小写后比对"兜底（配合数据库全文索引做近似匹配）。

**5）为什么问答要做成"异步 + 会话 + 轮询"？**
AI 回答要好几个步骤、花几十秒。同步等着会超时。所以后端**开个后台线程**跑，先把"会话号"返回给前端；前端每隔 1.5 秒来问一次"做到第几步了"。会话正文**每步自动落盘到本地 SQLite 检查点**（LangGraph 的 `SqliteSaver`），内存里只留一张"会话号 → 归属人 / 时间 / 模式"的最小索引——这样**进程重启后旧会话仍能被读出来**（历史会话也因此能被"记忆检索"引用）。用轮询而不是长连接，是实现简单、省掉常驻长链路的复杂度。

**6）为什么一定要有"降级回退"？**
大模型会抽风（超时、报错、返回乱七八糟）。所以每一步都留了后路：大模型挂了 → 用模板拼答案；Planner 挂了 → 退回老流程；解析 JSON 失败 → 也退回老流程；**MCP 工具通道连不上或调用失败 → 立即回落进程内的同一份实现**。**核心意思：AI 是加分项，不是命根子，没它也得能用。**

**7）为什么 Reviewer 只管"质检"，还限制最多 3 轮？**
Reviewer 干的是"挑毛病"：检查答案有没有瞎编引用、有没有漏、引用对不对。不通过就打回重做，但**最多 3 轮**——不然可能无限返工，浪费钱还卡死。3 轮还不过就强制收工并如实标注。

**8）为什么检索是"词法 + 向量"双路，而不是只跑一路？**
只跑词法（BM25 / 全文索引），问句换个说法就抓瞎；只跑向量，术语的精确匹配又容易漏。所以两路都跑：**词法路**（MySQL 全文检索 + LIKE 兜底）保证"术语命中"，**向量路**（本地 `bge-large-en-v1.5` 编码 + 余弦相似度）保证"语义相近也能捞回来"，再用 **RRF（倒数排名融合）** 合并成一份候选，最后交给 **BM25 精排**。向量模型在本地跑，不依赖外部服务；**重排仍是可替换的抽象层**——将来换别的精排算法，上层检索代码不用动。

**9）为什么只用 MySQL + 一份本地 SQLite，不搭外部搜索引擎 / 向量库服务？**
就一个大学生课程/个人项目规模：**业务数据全在 MySQL**（自带全文索引、支持中文，省得单独搭搜索引擎）；**会话检查点另存一份本地 SQLite**（只是个文件，随项目走，零运维）；**向量检索用本地模型 + 本地缓存文件**（不起向量数据库服务）。整体部署只要"装依赖、跑起来"，不引入需要额外维护的基础设施。

**10）为什么管理端接口单独挂 `/api/admin/**`？**
管理员功能和普通用户功能分开，在 `deps.py` 里统一用 `require_role("admin")` 拦一刀。这样以后加新管理功能，只要挂在这个前缀下就自动受保护，不用挨个改鉴权。

**11）为什么大纲编辑"不进数据库"？**
用户改大纲（调层级、加减章节、挂引用）是个"临时编辑"动作。为它建表、写保存接口，成本大于收益。所以：**前端本地编辑，点导出时才把内容传给后端生成 Word，导完就完事**。刷新页面就没了，符合"轻量增强"的定位。

**12）为什么工具层要包一层 MCP？**
工具（查库 / 查网 / 改写）原来只是"进程内直接函数调用"，包成 MCP 后变成"独立子进程 + 标准协议"。好处是**工具与编排解耦**：工具有进程边界，可单独测试、可替换，也能被别的客户端复用；代价是多了一次子进程启动与握手开销。所以它是**可选通道**——默认走 MCP，连不上或调用失败立刻回落进程内的同一份实现，**功能不退，只退实现方式**。

## 5. 各模块知识点 + 为什么这么设计（详解）

> 每个模块分两半：**① 涉及哪些知识点**（术语后面跟一句人话解释）；**② 为什么这块要这么设计**。

### 5.1 后端接口层（`main.py`、`app/routers/`、`app/schemas/`、`app/deps.py`、`app/config.py`）

**涉及文件**：`main.py`、`app/routers/*.py`、`app/schemas/*.py`、`app/deps.py`、`app/config.py`

**知识点**
- **FastAPI 路由 / 装饰器**：写个函数、加个 `@router.post(...)`，它就是一个接口。
- **Pydantic 模型**：定义"请求/返回的数据长什么样"，框架自动校验类型、自动生成接口文档。
- **依赖注入（`Depends`）**：接口执行前，框架自动把"当前登录用户"等东西准备好塞进来，你不用自己写。
- **`response_model`**：声明"这个接口返回什么结构"，FastAPI 按它过滤字段。
- **HTTP 状态码的讲究**：`200` 正常返回；`202` 表示"任务我收下了、还在异步处理"；`401` 没登录；`403` 登录了但没权限。
- **`lifespan` 生命周期钩子**：服务启动/关闭时执行的代码（这里用来建表、开定时器、装配任务处理器）。
- **CORS（跨域）**：浏览器安全策略，允许前端开发端口(5173)访问后端(8000)。
- **静态托管与 SPA 回退**：`StaticFiles` 托管前端打包产物；`GET /{path}` 兜底返回 `index.html`，让前端路由接管刷新。

**为什么这么设计**
- **接口只做"收 → 转发 → 返"，业务逻辑下沉**：路由文件保持很薄，改业务不用动接口，改接口不用动业务。
- **`routers` 与 `schemas` 分开**：契约只有一份来源。前后端争论字段名时，`schemas` 就是裁判。
- **异步任务一律返 `202` + 会话号**：因为问答/综述要跑几十秒，不可能同步等；先收下、给个号码牌，前端凭号码牌轮询。
- **前端产物由后端同源托管**：只跑一个进程就能既提供 API 又提供网页，部署最省事。

### 5.2 认证与权限（`app/security.py`、`app/deps.py`）

**知识点**
- **密码哈希（不可逆）**：密码不存明文、存哈希值，就算数据库泄露也倒推不出原始密码。
- **JWT（JSON Web Token）**：登录后发一张"签名通行证"，分 header.payload.signature 三段；带签名所以改不了，带过期时间所以会失效。
- **Bearer Token**：请求头 `Authorization: Bearer xxx`，这是携带令牌的通行做法。
- **用依赖注入当"门卫"**：`Depends(get_current_user)` 一行代码，接口就有了登录校验。
- **RBAC（基于角色的访问控制）**：按角色（`user` / `admin`）决定能进哪些接口。
- **401 与 403 的区别**：401 = "你是谁我不知道"；403 = "知道你是谁，但你没资格"。

**为什么这么设计**
- **用 JWT 而不是服务端 Session**：JWT 是无状态的，服务端不用存"谁登录了"，省内存、好扩展；问答那边虽有会话，但正文交给本地 SQLite 检查点、内存只留一张小索引，整体仍是轻量思路。
- **校验做成依赖，而不是每个接口手写**：避免漏写；新加接口时只要声明 `Depends(...)` 就自动受保护。
- **管理端统一前缀 + 统一拦截**：`/api/admin/**` 一律过 `require_role("admin")`。以后加管理功能，挂在同前缀下就自动安全，业务侧零改造。

### 5.3 数据层（`app/models.py`、`app/session.py`、`app/database.py`）

**知识点**
- **连接池**：数据库连接建好一批反复用，省掉频繁开关连接的开销（引擎与会话工厂在 `app/session.py`，`QueuePool` 带 `pool_pre_ping` / `pool_recycle`）。
- **ORM（对象关系映射）**：用 Python 类描述表，`app/models.py` 的 8 个模型是**表结构的唯一权威**，建表由 `Base.metadata.create_all()` 完成（原 `app/schema.sql` 已删除）。
- **Session 会话 + 事务**：一次请求内的多个操作共用一个 Session，最后 `commit()` 一起提交；FastAPI 侧用 `Depends(get_db)` 保证同一请求只开一个会话。
- **唯一索引**：强制某列（如论文唯一号）不能重复，从数据库层面兜住重复数据。
- **普通索引**：加速按某列查询/过滤。
- **FULLTEXT 全文索引（ngram 分词）**：让数据库能查"文章里含不含这个词"，ngram 切词让中文也能被搜到。
- **ORM 批量写入 / 冲突忽略**：`mysql.insert(...).on_duplicate_key_update(...)` 与 `prefix_with("IGNORE")`，一次提交多条、命中唯一键时按需更新或跳过。
- **多对多中间表**：`subscription_papers` 把"方向"和"论文"关联起来——一篇论文可能命中多个方向。
- **初始化引导（bootstrap）**：启动时自动建表、补默认管理员、补默认模型，保证"新装环境也能直接跑"。

**为什么这么设计**
- **单库 MySQL**：项目规模小，一个库够用，省去额外搭搜索引擎/向量库的运维。
- **用唯一索引去重，而不是只在代码里判重**：把"别存重"这件事交给数据库兜底，多个任务并发跑也不会重复入库。
- **用中间表建关系**：方向与论文天然多对多，硬塞进一张表会难查难维护。
- **模型为权威、由代码生成表**：表结构只在 `app/models.py` 维护一处，建表与结构校验（`scripts/align_schema.py`）都从模型出发，避免"SQL 文件与代码字段名对不上"。
- **少量原生 SQL 豁免**：全文检索这类 MySQL 方言能力保留 `exec_driver_sql` 原生 SQL，不为统一而牺牲能力。
- **启动自动初始化**：让"部署"这件事尽量少手工步骤，降低踩坑概率。

### 5.4 后台与调度（`worker/scheduler.py`、`worker/queue.py`、`worker/pipeline.py`）

**知识点**
- **后台线程 / 守护线程（daemon）**：主程序之外另开线程干活；daemon 表示主程序一退它就跟着退。
- **线程锁（Lock）**：多个线程动同一份数据时加锁，防止互相踩。
- **定时循环**：隔一段时间醒一次，检查"有没有该跑的任务"。
- **内存任务队列 + 幂等 enqueue**：在内存里排队分发任务；同一个 `task_id` 只入队一次（幂等 = 重复执行不产生额外效果）。
- **生产者-消费者**：调度器/接口是"生产者"往队列丢任务，worker 是"消费者"从队列取任务执行。
- **在途保护 / coalesce（合并窗口）**：上次任务还没跑完就别再发；错过的多个时间窗合并成一次跑。
- **重试分级**：分清"可重试的临时错误"和"不可重试的致命错误"，别对致命错误死磕。
- **四段式管道**：抓取 → 去重 → 筛选 → 入库，一段一段串起来。

**为什么这么设计**
- **用后台线程而不是独立进程**：本机单进程部署最简单，不用额外起 worker 进程、不用装消息中间件（Redis/RabbitMQ）。等量大了、要把队列换成外部的，业务代码也不用大改（队列做了接口抽象）。
- **队列要幂等**：定时器和"登录惰性触发"可能同时想跑同一个方向，用 `task_id` 去重就不会跑两遍。
- **必须 coalesce**：设备不是 7×24，关机期间攒了一堆时间窗，逐个补跑会"并发风暴"，合并成一次最省。
- **daemon 线程 + 启动时统一装配**：在 `main.py` 的 `lifespan` 里一次性注册 handler、启动队列和调度器，启动逻辑集中、一眼能看全。

### 5.5 抓取层（`sources/base.py`、`arxiv.py`、`semantic_scholar.py`、`wanfang.py`）

**知识点**
- **适配器模式 + 抽象基类**：定义一个"取数据"的统一接口，每个网站写一个适配器实现它。
- **统一中间格式（PaperRecord）**：把各家网站参差不齐的字段，统一成一种标准结构再交给上层。
- **限速（rate limit）**：控制请求频率，别把人家服务器打崩、也别把自己封了。
- **指数退避 + 抖动（jitter）**：失败就等 2、4、8… 秒再试；加随机抖动防止所有请求"同时"重试。
- **游标增量**：用"上次抓到的时间点"当起点，只拉新数据。
- **请求头伪装（UA / Referer）**：没有开放 API 的站点，靠模拟浏览器请求去拿数据。
- **无头浏览器渲染抓取**：页面内容是 JS 渲染出来的（不是静态 HTML），得真跑一个浏览器才能拿到。
- **字段规范化**：标题归一化、日期解析，统一成可比对、可入库的形式。

**为什么这么设计**
- **先抽基类再写适配器**：上层管道完全不关心"这家网站长什么样"，将来新增一个来源，只要再写一个适配器、不改管道。
- **限速 + 退避保底**：外部网站是别人的资源，克制请求是合规也是保命；退避能挺过对方临时 429/超时。
- **无 API 的站点单独走渲染抓取**：能拿到数据就先用上，但这套维护成本高、易变，所以文档里专门标注了"实测状态"。

### 5.6 检索与重排（`ai/retriever.py`、`ai/rerank.py`、`ai/meta_enhance.py`）

**知识点**
- **两阶段检索：召回 → 精排**：先用宽松条件把可能相关的都"捞"回来（保证不漏），再打分排序（保证顺序对）。
- **双路召回（词法 + 向量）**：文献库这一步同时跑两条路——**词法路**走 MySQL 全文索引、不够时用 LIKE 兜底；**向量路**用本地模型把问句和论文编码成向量、算余弦相似度——两路各自捞一批候选。
- **RRF（倒数排名融合）**：两路候选合并时，不看分数高低（两路分数量纲不同），只看各自"排第几"——排名越靠前贡献越大，最后按累计贡献排序。好处是不用调权重、天然抗量纲差异。
- **BM25**：老牌关键词打分算法，核心看三件事——词出现得多不多、这个词在整体里稀不稀、文档长短。融合后的候选最终交给它精排。
- **数据库 FULLTEXT 检索**：把"捞"这一步交给 MySQL 全文索引完成。
- **向量缓存（`ai/vector_recall.py`）**：论文向量算一次就存本地 `.npz`（用"id → 文本哈希"判断是否失效），文本没变就直接读缓存，不重复编码。
- **指令前缀（bge 系列模型）**：查询侧编码时加一句提示前缀、文档侧不加——这是该模型族推荐的用法，能让"问句"和"论文"落在同一个可比空间。
- **rerank 抽象层（策略接口）**：把"精排"做成一个可替换的模块，现在用 BM25，将来换别的算法不影响调用方。
- **元数据静态映射表**：期刊等级/分区/CCF 分类这些"查表就能确定"的信息，代码里注入，零大模型成本。
- **引用编号溯源**：答案里的 `[1] [2]` 严格对应文末来源清单，让每句话都能找到出处。
- **`user_id` 数据隔离**：检索时带上用户身份，保证只搜到自己有权看的数据。

**为什么这么设计**
- **两阶段**：只召回不精排，结果顺序乱、不相关；只精排不召回，容易漏。两段配合最稳。
- **双路召回 + RRF 已经落地**：只跑词法路，问句换个说法就抓瞎；只跑向量路，术语的精确匹配又容易漏。所以两路都跑、用 RRF 融合。此前"将来升级成语义检索"的设想已经实现；**精排则仍是可替换的抽象层**——将来换别的精排算法，上层检索代码不用动。
- **元数据不调大模型**：这类信息是确定的，查表即可，没必要花钱还引入不确定性。
- **引用编号**：大模型最爱"编造引用"，用编号 + 来源清单把答案钉在证据上，降低幻觉危害。

### 5.7 大模型 / 多 Agent（`ai/orchestrator.py`、`llm_provider.py`、`planner.py`、`reviewer.py`、`tools.py`、`rewrite.py`、`router_agent.py`、`analysts.py`、`summarizer.py`）

**知识点**
- **LLM 调用统一封装（`llm_provider`）**：所有大模型调用都走这一层，模型来源可配置（管理端能绑定模型）。
- **提示词工程（Prompt）**：把要求写清楚（角色、规则、输出格式），让模型照着干。
- **Function Calling（工具调用）**：让模型不只吐文字，而是吐"我要调用哪个工具、参数是什么"，程序照着执行。
- **JSON 结构化输出 + 解析容错**：要求模型吐 JSON，程序解析成对象；解析失败必须有兜底。
- **主-子 Agent 架构**：Planner（主）负责拆任务、调度；子 Agent / 工具负责专项执行；Reviewer 负责质检。
- **质检闭环 + 迭代上限（MAX_LOOP=3）**：不通过就返工，但最多 3 轮，防失控。
- **多层降级回退**：任意一步失败都有备选路径，保证整条链不断。
- **防提示词注入**：论文正文里如果藏了"忽略以上指令"，要让模型别被骗。
- **查询改写**：把用户的大白话问题，改写成"关键词 + 年份/来源/分类"这种结构化检索式。
- **LangGraph 状态图编排**：把一次问答画成一张"节点 + 有向边"的图，每个节点干一件事，边决定下一步走哪里；用"条件边"表达分岔（quick / normal / deep）与返工（review 不过关就退回 plan）。
- **编排档位（quick / normal / deep）**：按问题难度决定用多重的流程；**quick 通道额外做一次"LLM 英文关键词兜底"**——正则抽出的中文碎片关键词召回质量差，就先让模型改写出一批英文关键词再检索，失败则退回原关键词。
- **检查点持久化（`SqliteSaver`）**：图的每一步状态都自动写进本地 SQLite；进程重启后，旧的会话正文还能被读出来。
- **MCP（工具通道）**：把"查库/查网/改写"这几个工具包成独立子进程、走标准协议调用（设计理由见 §4 第 12 条），与编排进程解耦。
- **异步状态机（8 节点）**：把一次问答拆成 8 个有状态的步骤，逐步推进、可轮询。

**为什么这么设计**
- **大模型调用全走一层封装**：换模型、换厂商时只改配置，不动业务代码；也方便"按 Agent 绑不同模型"。
- **只在"要动脑"的地方用大模型**：成本与稳定性取舍——能用规则/查表解决的，绝不上大模型。
- **主-子 + 质检闭环**：比"一把梭问答"质量高（会拆解、会自查），但又用 `MAX_LOOP` 压住返工成本。
- **层层降级是硬要求**：大模型不可靠是常态；工程上必须"它挂了我也能用"，否则整个功能就是玻璃做的。
- **为什么改成"状态图 + 检查点持久化"**：原来的流程是"一大段顺序代码"，岔路和返工都靠 `if/else` 硬编码，越加越乱；改成 LangGraph 状态图后，**分岔与返工变成图上的边**，结构一眼可见、可单独测试。会话**正文每步落盘到本地 SQLite**（而不是只放内存），换来的是**进程重启后旧会话仍可读**——这同时也让"引用历史会话"的记忆检索有了稳定数据源。后台线程执行则保证接口不超时。
- **为什么工具层要再包一层 MCP**：见 §4 第 12 条——工具与编排解耦、可独立测试、可被别的客户端复用；连不上就回落进程内的同一份实现，功能不退。

### 5.8 文档导出（`app/routers/qa.py` 的 `_build_review_docx` + `python-docx`）

**知识点**
- **python-docx**：用 Python 代码生成 `.docx`（Word）文件，能设标题层级、段落、样式。
- **OOXML = ZIP + XML**：`.docx` 本质是个压缩包，里面是 XML；所以生成的文件开头是 `PK`（ZIP 标志）。
- **`StreamingResponse` 返回二进制**：把生成好的字节流直接推给浏览器，不落磁盘。
- **`Content-Disposition` 响应头**：告诉浏览器"这是要下载的文件、文件名是啥"；中文名要用 `filename*=UTF-8''` 编码，否则乱码。
- **前端 Blob 下载**：前端收到二进制后，用 `URL.createObjectURL` + 隐藏 `<a>` 触发保存。
- **大纲数据结构**：扁平数组 + `depth` 字段表示层级（不用嵌套树），增删改和排序都更简单。

**为什么这么设计**
- **文档在后端生成、不在前端拼**：格式统一可控、跨浏览器一致，前端只管下载。
- **导出传"大纲"而不是"一整坨文本"**：结构清晰，`depth` 能直接映射成 Word 的标题层级（Heading）。
- **编辑不落库**：这是临时编辑动作，为它建表/写保存接口成本大于收益，保持轻量。
- **中文文件名用 `filename*` 编码**：这是 HTTP 头的规范写法，不这么做下载下来文件名就是乱码。

### 5.9 前端（`web/src/`）

**知识点**
- **Vue 3 组合式 API**：用 `ref`（响应式数据）/ `computed`（派生数据）/ `watch`（监听变化）这些函数组织页面逻辑。
- **组件化 + props / emits**：父传子用 props，子通知父用 emits。
- **单页应用（SPA）+ 前端路由**：页面不整页刷新，切换靠前端路由；刷新靠后端"回退到 index.html"兜底。
- **路由守卫**：进页面前先检查"登录了吗 / 是不是管理员"。
- **Pinia 状态管理**：全局共享状态（比如"当前登录用户"）集中放这儿，各页面都能读。
- **Tailwind CSS**：用一堆小 class 直接拼样式，不另写 css 文件。
- **封装 API client**：所有请求都走 `api/client.ts`，统一注入 token、统一处理 401/403。
- **轮询 + 定时器清理**：定时去问后端进度；组件卸载时必须 `clearInterval`，否则定时器泄漏。
- **双态 UI（编辑 / 预览）**：同一个组件切换两种呈现，编辑态改数据、预览态只看效果。
- **Blob 下载**：见 5.8。

**为什么这么设计**
- **组合式 API 按功能聚合逻辑**：一段功能的相关代码放一起，好读好复用（不像老式选项式 API 把逻辑拆散）。
- **请求全走统一 client**：token 注入、错误处理都集中在一处，页面只负责调，不会每个页面各写一套。
- **用轮询而不是 WebSocket**：实现简单、对"非在线容错"更友好，省掉常驻长连接的复杂度。
- **编辑态数据由组件本地管理**：不往全局 store 里塞临时数据，导出完即弃，符合"轻量增强"定位。

### 5.10 编排与会话存储（`ai/orchestrator.py` + LangGraph / `SqliteSaver`）

**知识点**
- **一张图跑完一次问答**：`ai/orchestrator.py` 用 LangGraph 把流程画成 **8 个节点的状态图**——`rewrite`（改写）→ 分岔 → `execute_tools`（调工具）→ `summarize`（出草稿）→ `review`（质检）→ 收尾；另外 `plan`（规划）、`decompose`（拆解）、`library` / `web` / `memory`（三通道检索）也是图上的节点。
- **条件边决定走向**：`_route_after_rewrite`（quick 还是 plan）、`_route_after_plan`（下一步调哪些工具）、`_route_after_review`（收尾 / 退回重做 / 降级）——"分岔和返工"都表达成图上的边，不再是散落的 `if/else`。
- **汇总前移**：`execute_tools → summarize` 是**固定边**——先由 `summarizer` 出一份带引用编号的草稿，再交给 `reviewer` 去"质检这份草稿"。顺序是"先出稿、再挑错"，而不是反过来。
- **检查点（checkpoint）持久化**：图的状态每走一步就由 `SqliteSaver` 写进本地 SQLite 文件（默认 `data/qa_checkpoints.sqlite3`，可用环境变量 `LITRADAR_QA_DB` 覆盖；测试里用 `:memory:`）。
- **最小索引 + 正文分离**：内存里只留一张 `session_id → 归属人 / 创建时间 / 模式` 的小表；**会话正文全在检查点里**。`get_steps` / `get_result` / `get_raw` 都是"先查索引、再按 thread_id 从检查点读正文"。
- **两个图共用一个 saver**：问答图与综述图是两条独立的图，但共用同一个 `SqliteSaver` 实例（它内部自带线程锁，可跨后台线程使用）。
- **TTL 清理**：会话有 2 小时存活期；发起新会话时顺带清理过期索引，并删掉对应的检查点线程。

**为什么这么设计**
- **图 vs 顺序代码**：把控制流"画出来"以后，加一条岔路 = 加一条边，改动是局部的；而顺序代码里加岔路往往要动一大片。
- **正文落盘、索引留内存**：索引小、查询快，适合放内存；正文大、要长期留存，交给 SQLite。这样**进程重启后旧会话仍能被读出来**，前端不会拿到 404，历史会话也才能被"记忆检索"稳定引用。
- **复用同一 saver**：省一套存储装配，也让"问答会话"和"综述会话"的存储行为完全一致，排查问题时只看一处。
- **热词一致**：会话步骤 `detail` 里刻意不出现"证据 / 检索 / 复核"等开发术语（对齐产品口径），用户看到的是人话；技术细节留在日志与 `ai/trace.py` 里。

## 6. 建议的阅读顺序（想快速上手就按这个走）

1. 先看 `main.py` —— 知道服务怎么起来的。
2. 再看 `app/models.py` —— 知道有哪些表、数据长什么样（表结构的唯一权威）。
3. 走一遍**流程 A**：`worker/scheduler.py` → `queue.py` → `pipeline.py` → `sources/base.py`。
4. 走一遍**流程 B**：`app/routers/qa.py` → `ai/orchestrator.py` —— 先看那张 **LangGraph 状态图（8 节点 + 条件边，见 5.10）**，再顺着每个节点调用的 `ai/*` 一路看下去（改写 → 检索 → 汇总 → 质检）。
5. 想弄懂"工具是怎么跑在独立子进程里的"，看 `ai/tools.py` → `ai/mcp_client.py` → `ai/mcp_server.py`（连不上会自动回落进程内实现）。
6. 最后翻前端 `web/src/views/QaView.vue` + `api/client.ts` —— 看前后端怎么对上话。
7. 有疑问就回来查第 3 节的「功能 → 模块」表和第 5 节的「知识点 + 设计理由」。
