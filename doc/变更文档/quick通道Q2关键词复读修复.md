# quick 通道 Q2 查不到的两处问题：怎么修的

> 这批改动登记在《文档变更记录》§39。
> 只改了 quick 通道「怎么出关键词、怎么拿关键词去查」这两件事。检索算法本身的参数（top_k、候选池、RRF 的 k）没动；控制流程、会话存储、工具层、`app`、`web` 都没动。

## 1. 问题是什么

§35 给 quick 通道加了「检索前先让 LLM 把问句改写成英文关键词」。改完后 Q1、Q3 有起色，但 Q2（「论文中检索增强生成有哪些核心组件？」）一直查不到期望的两篇文献，全量回归里稳定 0/2，是题集里唯一一直挂零的题。

## 2. 为什么查不到

原因有两处，修好第一处才露出第二处。

### 2.1 第一处：模型把提示词里的例子当答案抄

上一版的提示词里写了示例关键词：

```
"Retrieval-Augmented Generation" + "Large Language Models"
"GraphRAG" + "Knowledge Graph"
```

本地模型（qwen3-8b）看到示例，就照抄一遍。Q1、Q2、Q3 三个不同的问句，模型吐出来的是同一组词（只有顺序不同），等于没有看问句。

这组词又刚好不顶用：

- `Retrieval-Augmented` 在库里 147 篇中占 82%，超过一半，MySQL 全文检索会把它当停用词，权重为零；
- `GraphRAG` 只有 4 篇，`Knowledge Graph` 只有 12 篇，都是很稀的词。

结果就是剩下这两个稀词主导排序，前 8 篇全是 GraphRAG 系列，Q2 期望的两篇（`#4`、`#102`）一个都进不去。

先确认过评测统计没有算错（`eval/run_eval.py` 里比对的是字符串 id，逻辑正确），确实是检索没查到，不是统计 bug。

### 2.2 第二处：模型写的是「类别名」，文献里写的是「具体东西名」

把示例删掉后，模型的输出变了，但还是不对。Q2 它给的是：

```
Retrieval Component, Generation Component, Information Retrieval, Language Generation
```

`#4` 那篇文献的摘要里写的是：

```
retrievers, vector databases, prompt-processing methods, and generator models
```

「Retrieval Component」和「retrievers」是两个说法，字面对不上，全文检索就抓不到。实测 `#4` 当时排在第 41 位（词法）、第 25 位（向量）、第 32 位（两路融合后）——不是被 top_k 截掉了，而是词没选对。

## 3. 怎么修的

### 3.1 第一步：去掉示例，加复读检查

| 文件 | 改了什么 |
|---|---|
| `ai/rewrite.py` | 提示词里**一个领域词都不写**，只写取词规则：第 1 个词是问句对象的英文全称；剩下的按问法取（问「有哪些/组成」就给各个组成部分，问「是什么/原理」就给关键环节或同类方法，问「区别」就给对比双方，问「效果/成本」就给指标名）。另外明写一句「不许把提示词里的字当关键词」。 |
| `ai/rewrite.py` | 加复读检查 `_is_prompt_echo`：如果模型输出的词**全部**是旧提示词里那 4 个示例词、而且问句本身没提到它们，就判定为抄示例，加一段纠正话再问一次。第二次还抄，就返回空，让上层退回原来的正则关键词（坏结果不写缓存）。 |
| `ai/rewrite.py` | 把「调一次模型拿关键词」抽成 `_quick_keywords`，方便重试时复用。 |

问句本身提到 RAG / GraphRAG 的题（Q1、Q3）不判复读，因为那是正常取词，不能顺手把这两题的输入也改了。

### 3.2 第二步：把「类别名」换回「具体名词」，两组词各查一次

提示词又试了两版，想让模型直接给摘要里出现的名词，都失败——它还是写 `Retrieval Component` / `Generation Component`。这属于本地小模型的能力上限，再调提示词没用。

于是改成：模型怎么写就怎么写，我们在后面把它翻译回去。

| 文件 | 改了什么 |
|---|---|
| `ai/rewrite.py` | 新增 `_agent_noun`：按英语构词规则把动作名词变成做事的名词——`generation→generator`、`retrieval→retriever`、`indexing→indexer`、`ranking→ranker`。规则只有三条（`-ion→-or`、`-al→-er`、`-ing→-er`），没有任何领域词表，也不看题集的期望文献。 |
| `ai/rewrite.py` | 新增 `_derive_alt_keywords`：输出里出现「X Component / X Module / X Part」这类标签时，把标签词干转成具体名词，再加上问句对象全称，组成**第二组关键词**，随 `alt_keywords` 一起返回。没有标签就不带这个字段，返回结构和以前一样。 |
| `ai/retriever.py` | 原来 `search_library` 的主体抽成 `_rank_keywords`（一组词查一次：词法 + 向量 + 融合）。`search_library` 发现有 `alt_keywords` 就再用第二组词查一次，然后由 `_fuse_keyword_sets` 按名次把两次结果合起来（RRF，只比名次，不加权）。没有 `alt_keywords` 时行为和以前完全一样。 |
| `ai/orchestrator.py` | quick 节点把 `alt_keywords` 传进检索参数，并在步骤说明里多写一句「派生词集 N 个」，方便看日志知道走没走第二组。 |
| `tests/test_rewrite_quick_guard.py`（新） | 5 个测试：抄示例会重试一次、两次都抄返回空、问句含 GraphRAG 不误判、正常输出不重试、提示词里确实没有领域词。 |
| `tests/test_rewrite_alt_keywords.py`（新） | 12 个测试：构词规则 7 组、标签转名词、没有标签不转、返回里带 `alt_keywords`、融合后保留第一名、检索层带/不带 `alt_keywords` 的调用次数。 |
| `tests/test_orchestrator_paths.py` | 只改 1 处断言：关键词条数从「2-5 个」改成「3-5 个」。 |

### 3.3 为什么一定要查两次

| 用哪组词查 | `#4` | `#102` |
|---|---|---|
| 模型原样输出（类别名） | 查不到 | 查到 |
| 类别名 + retriever + generator | 查不到 | 查到 |
| 只给具体名词（Retriever、Vector Database…） | 查到 | 查不到 |
| 两组词各查一次再按名次合并 | 查到 | 查到 |

一组词只能覆盖一种说法：写类别名就丢具体名词那篇，写具体名词就丢类别名那篇。查两次再把名次合起来，两边的头部都能保住。

多查一次的代价实测可忽略：一次 `search_library` 约 0.28 秒。

## 5. 结果

1. **Q2 从 0/2 修到 2/2，连跑 5 轮都是 2/2**（3 轮 quick + 2 轮全量）。
2. 两处原因分别对应两步改动：抄示例靠「删示例 + 复读检查」解决（0/2 → 1/2）；类别名对不上具体名词靠「构词规则转名词 + 两组词各查一次」解决（1/2 → 2/2）。
3. 构词规则是纯英语拼写规则，不写任何 RAG 领域词，也不拿题集的期望文献当条件，不会过拟合到这套题上。
4. 别的题没有变差：Q4、Q6、Q7、Q8、Q9 两轮和改前逐题一致。Q5 第一轮 2/3、Q10 第一轮 1/2 是原来就有的跑动波动，第二轮回到 3/3、2/2。

## 6. 没做的 / 还没解决的

- **Q1 会抖**：五轮分别是 2/2、2/2、1/2、0/2、2/2，改前是固定 1/2。原因是关键词由本地模型每次现写，个别轮次会写「retrieval model / generated text」这类泛词，把期望文献压下去。这个抖动在 §35 就有，不是这批带来的。要压住得固定采样温度或加词集校验，留给下一批。
- **Q3 一直 1/2**：缺 `#58`，原因是 quick 只查一轮就结束（§35.5 记录过），这批没有处理。
- **Q8 偶尔回退**：日志里出现过「Planner 不可用，回退 v3 固定流水线」，这是 deep 路径的老问题（§35.4），跟这批无关。
- **负缓存没做**：复读检查在这几轮里一次都没触发，代价可以忽略。

## 7. 怎么撤回

改动集中在三个文件里的几个函数，直接还原这三个文件就回到 §35 的行为：

```
git checkout ai/rewrite.py ai/retriever.py ai/orchestrator.py
```

不涉及环境变量，也不涉及数据迁移。

## 8. 跑评测前的提醒

先确认向量检索模型加载成功（`vector_recall.available()` 为真），否则整轮会退化成只查词法，数据不能和别的轮对比。

这台机器上踩过两次：

- 可用内存只剩约 2.9GB 时，加载 bge 模型报 `OSError: 页面文件太小`，那一轮作废；
- 可用内存不足时，加载模型的过程中直接段错误（0xC0000005，报错停在 `threading.Thread.start`），整轮没有任何输出就退出。

跑之前先 `ollama stop <模型名>` 把本地大模型占的内存放掉（这次放完可用内存回到约 7.6GB），再跑就正常。
