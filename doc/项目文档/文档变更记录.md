## 2. 借鉴来源

本次迭代的可借鉴功能均来自对 **NNScholar-search（nnscholar-search-7.17.zip）** 项目的源码分析：

- 分析报告：`output/nnscholar-search-7.17_项目分析报告.md`
- 项目定位：集成 DeepSeek AI 的医学/生物学术文献检索与深度分析平台（Flask + SocketIO + DeepSeek + Embedding）
- 六项借鉴点与来源：
  - a. AI 查询改写 ← `deepseek_service.generate_search_strategy`（自然语言 → PubMed 布尔检索式，失败回退原 query）
  - b. 结果重排 rerank ← `embedding_service` 语义重排 + TF-IDF 本地兜底（本项目中以 BM25Okapi 替代 TF-IDF 并抽象接口）
  - c. 本地元数据增强 ← `journal_service` + `data/journal_metrics`（IF/JCR/CAS 分区，ISSN→期刊名多级回退注入）
  - d. 多模式检索 ← `api_routes.search_papers` 的 `mode`（single / paragraph / strategy）
  - e. 异步任务 + 进度反馈 ← `async_task_service` 任务队列 + SocketIO 进度推送（本项目对齐"惰性 worker + 前端轮询"）；文献引用网络图谱 ← `literature_tracking_service`（Connected Papers 风格）
  - f. 工程教训 ← NNScholar"清单宣称 vs 实际完成度"偏差（README 勾选但多为 UI 占位）

## 4. 工程教训（经验备注，不进主体文档）

- **功能承诺须收敛为真实交付项**：NNScholar 的 README / 功能清单宣称大量功能，实际多为 UI 占位（如"深度分析工具箱 15 项"多数按钮仅弹"开发中"提示）。文献雷达项目文档所有需求/模块必须与真实交付一一对应，清单宣称 ≠ 完成度。
- **单一事实源、单架构演进**：NNScholar 存在旧版单文件 `app_original.py` 与新版分层架构并存、根目录散落大量调试脚本，接手与维护成本高。本项目保持单架构演进，各文档对同一机制（如 rerank、查询改写）只在归属文档详述、其余交叉引用，避免互相矛盾与重复。
- **可升级抽象先于技术选型**：rerank 抽象层接口先行（BM25Okapi 默认、embedding 预留），避免后续升级引发大面积改动。

  **结论：存储迁移等价成立**。⚠️ 计划原定「命中率 / reviewer 通过数一致、token ±10%」的硬阈值**对单次跑不具判别力**：同一份 main 家族代码的历史三次跑自身即波动于 **14/23 · 90397 token**（111331）、**15/23 · 97479 token**（130406）、**12/23 · 61659 token**（本次新基线）。Phase 2 的两项内容指标**均落在该波动带内**（命中并列带内最高，token 低于两次 main 历史跑）。漂移经定位为 **LLM 非确定性**：主要来自 planner / reviewer 的调度选择——Q8 基线 2 轮 / 8 条证据 / 7382 token → 本轮 3 轮 / 19 条 / 29756 token（单题占全部 token 增量的 85%）；Q9 基线 3 轮 + 5 处超时 → 本轮 1 轮通过。据 spec §7 风险表与实现计划 Task 4 Step 4（非确定性 → 在记录标注并交用户裁定），**用户裁定接受 Phase 2 通过**。

### 33.3 要点备忘与遗留

- **token 基准带结论（对设计 D4 的实测修正）**：设计 §7.4 曾预期「每轮多一次汇总 → token 显著上升，需重设基准带」。实测**未上升**（86712 → 74257，反而下降约 12.5k），原因是 deep 题本次全部 1 轮收敛（`MAX_ITERATION=3` 未触顶）、且首出草稿的输入比收尾草稿更小；差值落在历史波动带内，**无需重设基准带**。设计 §8「token 显著上升」一栏应据此降级为「按轮次线性增长，1 轮收敛时与改前近似」。
- **实现时发现并补修的一处语义缺口（重要，非设计文档所列）**：原设计只把「汇总」前移，未处理 **复审内补跑分析师** 的时序——`_maybe_backfill_analysts()` 在 review 节点内执行，改后汇总已在其之前，若该轮就是收尾轮（通过 / 达上限），末轮草稿将**缺失刚补跑出的分析师内容**（§30 落地的多视角需求通道会因此空转）。故在 `_node_review` 增加「补跑且收尾 → 重跑一次 `_step_summarize`」。该刷新不出现在 quick / fallback / 零证据路径（那三条不触发补跑）。
- **```plan_degraded``` 行为变更（设计 §8 已知风险，实测确认）**：改后降级轮由「直连 finalize 立即收尾」变为「经 summarize 出草稿 → 进 review → 可能再触发 retry」，轮次由 `max_rounds` 兜底。四路径集成用例 `test_deep_retry_round_plan_failure` 的期望值已随之改写（`review_calls` 1 → 3、`iteration_count` 2 → 3、`iteration_limit` 置位）。**代价**：Planner 连续降级时不再提前结束，会烧满轮次（token 上升）；**收益**：降级轮不再无产出。若后续实测发现降级场景 token 明显恶化，可另案改为「summarize 出边按 outcome 条件分流（降级 → finalize）」。
- **测试落位与设计文档 §5.4 的一处偏差**：设计原列「新增 `tests/test_orchestrator_summarize_order.py`」，实施时将新用例并入既有 `tests/test_orchestrator_paths.py`——该文件已持有四路径桩件夹具（`stub`），另起文件须复制整套 patch 装配，违反 DRY，故合并（夹具新增 `synth_calls` 计数一项）。

### 34.2 关键故障与修复：Windows 加载器锁死锁（本次唯一阻塞项）

- **现象**：MCP 开启后 `library_search` 经子进程调用**永久挂死**（30s / 120s / 180s 均超时，异常 message 为空 = `TimeoutError`），随后 `_unavailable` 置位 → 整轮评测全部回落进程内，MCP 形同未启用；而 `list_tools`（2.1s）与 `rewrite_query` 均正常，**`LITRADAR_VECTOR_RECALL=0` 时经 MCP 0.1s 正常返回**。
- **定位过程（逐层排除，均有对照实测）**：
  1. 服务端插桩（stderr 标记 + `ai/retriever.py` 分段标记）→ 卡点收窄到 `_fuse_vector`；
  2. 再插桩 `ai/vector_recall.available()` 前一语句 → **确认卡点是首次 `import sentence_transformers`**；
  3. `faulthandler.dump_traceback_later` 抓真实堆栈 → 工具线程阻塞在 C 扩展 `create_module`，链路 `sentence_transformers/util/similarity.py → sklearn → scipy.linalg.blas`；
  4. 已**逐一排除**的假说：**线程上下文**（主线程 / anyio 工作线程 / asyncio 事件循环线程各跑一次 `search_library`，均 ~10.5s 正常）、**spawn 参数**（`stdin/stdout=PIPE` + `CREATE_NO_WINDOW`）、**Windows Job Object**（保活 job 句柄后对照，A/B/C 三组均正常）、**stderr 继承**、**job 句柄 GC**。
- **根因**：`sentence_transformers` → `sklearn` / `scipy` 的 C 扩展**首次导入发生在工具调用阶段**，与 stdio 事件循环的**并发 import 争抢 Windows 加载器锁**，形成跨线程死锁（纯 asyncio 进程里导入时事件循环线程空闲，故探测脚本全部通过——这正是该故障此前难以复现的原因）。
- **修复**：`ai/mcp_server.py` 新增 `_warmup()`，在 `mcp.run()` **之前**（单线程、事件循环尚未启动）先 `import sentence_transformers`，把重依赖首次导入前移；导入失败静默忽略（检索层自带回落）。修复后实测 `call_tool -> list len=8 t=1.5`、`unavailable flag: False`。
- **回归防护**：`tests/test_mcp_server_integration.py::test_main_warms_up_before_serving` 断言 `main()` 的执行顺序为 `["warmup", "run"]`。

## 43. 收尾 Q2 / Q3：检索词补分类学与对照基线 + 确定性扩展（2026-10-21）

> 分支：`feat/summarize-before-review`（沿用）
> 这批改什么：quick 通道的**取词规则**（提示词加两条）、**检索词扩展**（纯规则）、**检索口径**（条数 12→14、向量权重 5→1.8）。
> 没改什么：normal/deep 的控制流、Planner/Reviewer/Summarizer 提示词、`ai/retriever.py`、MCP、`app/*`、`web/*`、数据库。

### 43.1 问题是什么

§42.6 留了两条尾巴，其余文献都已稳定召回：

- **Q2 不稳**：期望的 `#102` 只有和 taxonomy / survey 这类「综述、分类学」词一起检索时才排得进来，而 quick 的提示词从没要求过这类词。Q2 实际输出是 `retriever / generator / document index / reranker`，`#102` 向量路 3~14、词法 37~44，融合后 16 名，落榜。
- **Q3 会 0/2**：期望的 `#58` 是「标准 RAG」那篇对照文献。实测只有检索词里出现字面 `standard RAG` 时，它才进词法路第 3~5 名；否则词法 15~63、向量 42~58，怎么融合都进不了前 12。

另外探针还测到一个小坑：deepseek-flash 即使 `temperature=0`，也有约两成概率返回不是 JSON 的文本（Q3 五次里一次、Q2 三次里一次），这时整轮直接退回正则碎片词，等于白白丢一轮。

### 43.2 根因

| 题 | 缺的词 | 缺了以后的名次 |
|---|---|---|
| Q2 | `taxonomy`（综述/分类学视角） | `#102` 词法 37~44，向量 3~14，融合 16 名 |
| Q3 | `standard RAG`（对照基线） | `#58` 词法 15~63，向量 42~58 |

不是检索层算错，而是**问句里根本没问「和常规做法比」，模型就不会生成对照词**；同理「有哪些组件」也没问「有没有人做过综述」，模型不会补 taxonomy。检索层拿到什么词就按什么词排，词不对，名次自然上不去。

再加一层词形问题：语料摘要里写 `Graph RAG`，而 MySQL 分词把 `GraphRAG` 当一个 token，词法路两端对不上；同理摘要里更常用 `RAG / LLM`，长全称在 BM25 里词面对不齐。

### 43.3 方案（三件事，互相配套）

1. **提示词补两条取词规则**（`QUICK_PROMPT` 第 6、7 条，不含任何领域具体术语）：
   - 第 6 条：问某个方法的定义/原理，且该方法是另一个方法的变体 → 补一条「原方法的常规做法」，写成 `standard <原方法名>`。
   - 第 7 条：问「有哪些 / 组成 / 分几类」→ 补一个综述或分类学视角的英文术语。
   - 实测 5 次 Q3 的 4 次有效输出**全部**带 `standard …`，Q2 的 2 次有效输出**全部**带 `taxonomy`；Q1 不受污染。
2. **确定性扩展**（`ai/rewrite.py`，纯构词规则，零 LLM、无领域词表），把模型给的写法补成语料实际写法：
   - 复合词拆形：`GraphRAG` → `Graph RAG`。
   - 缩写派生：`Retrieval-Augmented Generation` → `RAG`；`standard Retrieval-Augmented Generation` → `standard RAG`；`Large Language Models` → `LLM`。缩写短于 3 个字母不派生（`KG / DR / RM` 这类两字母在本语料里是噪声）。
   - 限定词缩写：`Graph Retrieval-Augmented Generation` → `Graph RAG`（首词是限定词时，缩写只取它后面的大写实词）。
   - 扩展词**直接并入 `keywords`**，词法路与向量路读同一份。实测只扩词法路、向量路仍用原词时，Q3 会掉回 1/2，必须两路一起扩。
3. **重新调检索口径**：`QUICK_LIBRARY_TOP_K 12→14`、`QUICK_VECTOR_WEIGHT 5.0→1.8`。
   - 词补对之后，`#58` 词法已到第 3~4 名，向量仍 26~35；`#42` 反过来词法 26~37、向量 8~9。两篇一个靠词法、一个靠向量，权重 5 会把 `#58` 压出去，等权又会把 `#42` 压出去。
   - 离线扫参：`vw` 在 1.5~2.0、条数 14 时八组词集全中；取中间的 **1.8**，条数放到 14 留 2 个名次的余量。

## 45. 问答编排并发闸门（2026-10-24）

> 这批改什么：给问答流水线和上游 LLM 调用各加一道并发闸门，超出上限的请求排队等槽位，不再无限派发线程。顺带修了 MCP stdio 的 stdout 污染、给 Reviewer 补了一条诊断日志。
> 没改什么：编排流程、路由、Planner/Reviewer/Summarizer 的输入输出契约、前端、数据库。

### 45.1 需求

`/api/qa/ask` 每收到一个请求就 `threading.Thread` 起一条流水线，没有上限；单条流水线内部的 `run_analysts` 还会再派生 3 个 analyst 线程。10 个用户同时提问 = 瞬时 10 条流水线 + 最多 30 个分析师线程，一起打上游模型。上一轮压测（10 并发）虽然全部跑完，但上游被瞬时打满，且看不出任何节流手段。

### 45.2 方案

两道 `threading.BoundedSemaphore`，互相独立：

| 闸门 | 位置 | 管什么 | 缺省上限 | 环境变量 |
|---|---|---|---|---|
| 流水线闸门 | `ai/orchestrator.py` | 同时在跑的问答/综述流水线条数 | 10 | `LITRADAR_QA_MAX_CONCURRENCY` |
| LLM 闸门 | `ai/llm_provider.py` | 同时在途的上游 `chat()` 调用数（所有 agent 共用） | 8 | `LITRADAR_LLM_MAX_CONCURRENCY` |

- **排队不改变接口语义**：`/ask` 仍立即返回 202，排队发生在后台线程里。排队中的会话只是步骤停在 pending，前端照常轮询。
- **槽位只在关键区持锁**：LLM 闸门只包住 `client.chat.completions.create(...)`，排队等槽位的时间不计入请求超时（超时从拿到槽位之后开始算）。
- **异常值兜底**：环境变量非法（`0`、`abc`）时分别回落为 1 和缺省值，不会因为写错变量把服务卡死。

### 45.3 改了哪些文件

- `ai/orchestrator.py`：新增 `QA_MAX_CONCURRENCY` / `_qa_max_concurrency()` / `_PIPELINE_SLOTS`；`_run_pipeline` 与 `_run_review_pipeline` 的 try/finally 整体包进 `with _PIPELINE_SLOTS:`。
- `ai/llm_provider.py`：新增 `LLM_MAX_CONCURRENCY` / `_llm_max_concurrency()` / `_LLM_SLOTS`；`chat()` 的上游调用包进 `with _LLM_SLOTS:`。
- `ai/retriever.py`：`search_web` 的异常日志从 stdout 改到 stderr。该模块也会在 MCP stdio 子进程里执行，stdout 是 JSON-RPC 通道，往 stdout 打印会把协议报文冲掉，客户端解析失败后无谓降级回进程内实现。
- `ai/reviewer.py`：输出无法解析时多打一行原文前 120 字，便于定位是空响应、非 JSON 还是截断；`REVIEW_MAX_TOKENS` 由 1024 提到 2048（空响应根因见 §45.6）。
- `tests/test_concurrency_gate.py`：新增 3 例（流水线闸门峰值、LLM 闸门峰值、环境变量解析与兜底）。

### 45.4 对照实验（同为 10 并发、同一 10 道题）

| 配置 | Reviewer 失败 | 墙钟 | 端到端 p50 |
|---|---|---|---|
| 无闸门（原状） | 4/10 | 63.5s | 48.2s |
| 流水线 5 + LLM 8 | 3/10 | 180.0s | 117.3s |
| 流水线 5 + LLM 3 | 4/10 | 166.2s | 116.5s |
| 流水线 10 + LLM 8（最终） | 4/10 | 188.1s | 92.4s |
| 流水线 10 + LLM 8 + `REVIEW_MAX_TOKENS=2048` | **0/10** | 147.3s | 90.7s |

结论：

- 把流水线压到 5 只让整体变慢（63s → 180s），Reviewer 失败率没有实质改善；
- 把 LLM 压到 3 与放到 8，失败数一样（都是 4/10），说明失败与上游并发无关；
- 所以流水线闸门从 5 收回 10：正常并发不受影响，它的真实作用是拦住「几十个请求同时派生几十个 analyst 线程」的极端情况；LLM 闸门保留 8，只为不把上游打爆；
- Reviewer 的空响应靠放大输出预算解决：1024 → 2048 后失败从 4/10 降到 0/10，服务端日志里「复审输出无法解析」「复审失败」均为 0 次。所以根因是推理 token 把输出预算吃光，正文为空，不是并发问题。

### 45.5 测了什么、结果多少

1. `pytest tests/ -q` → **172 passed**（新增 3 例）。
2. 轻接口 20 并发（health/login/subscriptions/unread/papers）零错误，health p95 15.7ms。
3. 问答 10 并发（最终配置）：10/10 完成、Reviewer 零失败，墙钟 147.3s、端到端 p50 90.7s，答案 1269–1943 字、引用 11–14 条，无截断。

### 45.6 还没解决的 / 要知道的

- **Reviewer 空响应的根因是输出预算，不是并发**。诊断日志实证上游返回**空字符串**（`原文前 120 字: ''`），不是超时、不是 JSON 截断、不是限流；加闸门前 4/10，加闸门后仍 4/10。把 `REVIEW_MAX_TOKENS` 从 1024 提到 2048 后，同样 10 并发降到 0/10。
- 预算翻倍会带来每次复审的 token 成本上升（正常情况下输出远小于 2048，实际只多用几十 token），但若上游继续退化到「推理 token 吃光 2048」，仍会偶发空响应，届时可再上调或改为空响应重试一次。
- 闸门上限是进程内计数，多 worker / 多进程部署时各自计数，不是全局上限。

### 45.7 怎么撤回

- **只关闸门不想回退代码**：把 `LITRADAR_QA_MAX_CONCURRENCY` / `LITRADAR_LLM_MAX_CONCURRENCY` 设成很大的数即可（如 1000）。

## 46. 问答链路的超时拒绝、429 退避与结果缓存（2026-10-24）

> 这批改什么：给排队加等待上限（等不到就提示「请求过多」）、给 429 加指数退避重试、给问答结果加进程内 TTL 缓存。
> 没改什么：并发闸门的上限值（仍是流水线 10 / LLM 8）、单次上游调用超时（仍是 60s）、编排流程、前端、数据库。

### 46.1 需求

1. 请求多了不能无限排队，15~30s 内拿不到执行机会就告诉用户「当前 API 请求过多，请稍后再用」；
2. 用信号量限制同时发给上游的请求数，不狂轰（第 45 条已落地，本次只补等待上限）；
3. 429 要捕获并做指数退避，不能无脑重试；
4. 相同问句直接返回缓存结果，不再调上游。缓存后端倾向先不上 Redis。

### 46.2 方案

**① 排队上限（20s）**

流水线槽位不再无限等待：`acquire(timeout=20)`，拿不到就把会话标成 `error='当前 API 请求过多，请稍后再试'` + `finished=True` 并落盘，然后直接返回。

- `/ask` 仍是立即返回 202，用户靠轮询 `/result` 看到这条提示（前端已有 `result.error` 红框，零改动）。
- 20s 落在 15~30s 区间内；单次 LLM 调用超时保持 60s（本地大模型汇总阶段单次就要 30~40s，缩到 30s 会误杀）。
- 环境变量 `LITRADAR_QA_QUEUE_TIMEOUT`（秒，缺省 20，非正数回落默认）。

**② 429 指数退避**

- 只重试「限流」：`openai.RateLimitError` 或任何 `status_code=429` 的异常；超时、5xx、连接错误一律不重试（重试也救不了，交给上层降级）。
- 最多重试 3 次，间隔 1s → 2s → 4s，每次加 0~0.3s 抖动，避免多个线程同时醒来再次撞车。
- 重试期间不释放 LLM 槽位：上游正在限流，放别的请求进来只会继续被拒。
- 只有最终失败才写一条错误 trace，重试过程不刷记录。

**③ 问答结果缓存（进程内 TTL）**

为什么先不上 Redis：服务是单进程 uvicorn（流水线跑在后台线程），进程内字典就能覆盖「同一用户重复提问同一问题」；Redis 要多一个服务、多一个依赖、多一份运维，等真上多 worker / 多机再换。缓存读写都收在 `ai/qa_cache.py`，届时只改这一个文件。

| 项 | 口径 |
|---|---|
| 缓存键 | `user_id + 归一化问句 + mode + rewrite + enable_planner` |
| 归一化 | 合并连续空白 + 统一小写（「RAG 是什么」与「 rag  是什么 」同键） |
| 缓存值 | 上次终态快照：答案/要点/引用、改写结果、步骤条、工具调用、复审意见、迭代次数 |
| TTL | 1800s（文献库按天更新，30 分钟足够新） |
| 上限 | 200 条，超出淘汰最久未访问 |
| 失效 | TTL 到期 / 超上限淘汰 / worker 入库新文献后按用户清空 / `LITRADAR_QA_CACHE=0` 整体关闭 |
| 不缓存 | 报错、空答案、综述会话 |

命中时的行为：仍创建会话、仍落盘终态，只是不派生流水线线程、不调上游；步骤条 detail 后缀标注「缓存命中」，用户能看出这是回放。

**评测必须关缓存**：`eval/run_eval.py` 启动时强制 `LITRADAR_QA_CACHE=0`，否则同一题第二次运行会直接回放旧答案，命中率与 token 统计全部失真。

### 46.3 改了哪些文件

- `ai/qa_cache.py`（新增）：进程内 TTL 缓存（归一化、键构造、读写、按用户清空、开关）。
- `ai/orchestrator.py`：`_run_pipeline` 改为 `acquire(timeout=_qa_queue_timeout())`，超时写友好错误；新增 `_cache_key` / `_apply_cached` / `_cached_steps` / `_store_cache`，`ask()` 命中缓存时直接返回终态。
- `ai/llm_provider.py`：新增 `_is_rate_limited` / `_retry_delay` / `_create_with_retry`，429 指数退避（1/2/4s + 抖动），其他异常不重试。
- `worker/pipeline.py`：本轮有新文献入库时调用 `qa_cache.clear_user(sub['user_id'])`，避免回放旧文献集的结果。
- `eval/run_eval.py`：启动时置 `LITRADAR_QA_CACHE=0`，保证评测真实跑链路。
- `tests/test_qa_cache.py`（新增 8 例）、`tests/test_llm_retry.py`（新增 3 例）、`tests/test_concurrency_gate.py`（补排队时长的环境变量断言）。

### 46.4 测了什么、结果多少

1. `pytest tests/ -q` → **183 passed**（172 + 11 例新增/扩展）。
2. 排队拒绝端到端：把上限临时设成 1 条、排队上限 2s，连发两个问题 → 第二个 **2.1s 返回 finished + 「当前 API 请求过多，请稍后再试」**，第一个照常跑完。
3. 缓存端到端：同一问句连发两次 → 首次 82.4s / 1785 字 / 11 条引用；第二次 **0.0s**、答案与引用完全一致、步骤条含「缓存命中」；服务端日志出现 3 次「命中问答缓存」，无 traceback。
4. 429 退避：单测覆盖「两次 429 后成功 = 调用 3 次 + 间隔 1s/2s」「4 次全 429 = 首次 + 3 次重试后原样抛出」「非 429 只调用 1 次」。

### 46.5 还没解决的 / 要知道的

- 缓存是**进程内**的：重启服务即清空，多 worker / 多进程之间不共享；真要横向扩容时把 `qa_cache` 换成 Redis 实现即可，调用方不动。
- 缓存只按 TTL 与「有新文献入库」失效，不会感知论文内容被外部改写；TTL 内的答案反映的是缓存时刻的文献集。
- 排队上限只卡「开始执行」这一环：已经在跑的流水线内部，LLM 槽位仍是排到为止（否则会误杀正常长任务）。10 并发实测下正常完成，说明这个等待量可接受。
- 缓存命中与正常执行的步骤条内容一样（只多一个后缀），前端不需要新增字段；若以后要在结果页显著标「缓存」，需双方约定新字段。
